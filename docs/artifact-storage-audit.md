# Хранение планов, спецификаций, документации и контекста

## Статус и область проверки

Аудит после обновления до `main` `86b39cc0ac0d30de243967c216f7718ffed7050a`,
с локальным незакоммиченным прототипом SessionBrief для issue #168.
Проверены код, инструкции владельцев артефактов, upstream-документация и
временные примеры с реальными вызовами helpers. Исходный код в ходе аудита
не изменялся. Целевая раскладка ниже ещё требует реализации и миграции.

Речь о файлах **проекта, использующего расширение**. Репозиторий самого
расширения хранит инструкции, схемы, документацию и fixtures; его запрет на
коммит корневых `openspec/` и runtime-каталогов нельзя переносить как общую
политику Git в проекты-потребители.

## Вывод

AI Factory должен владеть идентичностью и жизненным циклом плана. План связывает
требования, решения, задачи и проверки, но постоянные знания о проекте и результаты
отдельных запусков имеют собственные места хранения и сроки жизни.

Нужны три устойчиво различимых вида материалов:

1. Действующие знания и требования проекта: спецификации возможностей, архитектура,
   принятые решения, правила, документация и проверенные справочные материалы.
2. Материалы изменения: исходный запрос, предлагаемые изменения требований,
   варианты решения, задачи, критерии приёмки и ссылки на используемые документы.
3. Производные материалы исполнения: SessionBrief, указатели, контекст сессии,
   результаты проверок, журналы и представления для инструментов.

Один план может одновременно содержать user stories, сценарии, C4 и ADR.
Основной формат требований и набор дополнительных документов — разные настройки.
SDD-профиль определяет глубину проработки; включённый инструмент определяет
доступную операцию над поддерживаемым представлением.

## Что сейчас расходится с этой моделью

### 1. Выбор инструмента переопределяет расположение и владельца планов

В [tool-config.mjs](../scripts/tool-config.mjs) `toolArtifactPaths()` при наличии
`aifhub.tools` заменяет явно заданные `paths.plans` и `paths.specs`:

| Исходные пути | OpenSpec | Эффективные пути |
|---|---|---|
| `planning/tasks`, `knowledge/specs` | `false` | `.ai-factory/plans`, `.ai-factory/specs` |
| те же | `true` | `openspec/changes`, `openspec/specs` |

Оба результата воспроизведены прямым вызовом. Это текущий контракт `main`,
противоречащий новому требованию из [ADR 0005](adr/0005-ai-factory-plan-methodologies.md).
Изменение только YAML не создаёт нужную общую модель хранения.

### 2. SessionBrief не принимает новый формат конфигурации

В [session-brief.mjs](../scripts/session-brief.mjs) проверяется только старое
`aifhub.artifactProtocol`. На одинаковых корректных артефактах:

- `artifactProtocol: openspec` → успешная компиляция;
- только `tools.openspec: true` → `blocked`, `openspec_protocol_required`,
  хотя `readProjectConfig()` правильно определяет режим `openspec`.

Это несовместимость локального прототипа с обновлённым `main`. Имеющиеся тесты
SessionBrief создают legacy-конфигурацию и этот случай не покрывают.

### 3. Пути runtime разрешаются неодинаково

При `paths.state: runtime/state` функция `ensureRuntimeLayout()` создаёт
`runtime/state/audit-change`, но SessionBrief пишет в
`.ai-factory/state/audit-change/context/`. Это воспроизведено на одном проекте.

[Provider evidence](../scripts/aifhub-providers.mjs) тоже использует фиксированный
`.ai-factory/qa/<id>/providers/`. Правила исключения runtime из
[providerRevision()](../scripts/provider-files.mjs) знают только стандартные
`.ai-factory/qa`, `.ai-factory/state` и `.ai-factory/rules/generated`.
В пробе запись в стандартный state не меняет digest, а запись в настроенные
`runtime/state` или `runtime/qa` меняет его. Часть потребителей поддерживает
настройку путей, часть продолжает работать с константами.

### 4. Проверки свежести охватывают не все необходимые источники

В отдельном временном Git-репозитории изменение файла
`.ai-factory/plans/audit.md`, исключённого через `.gitignore`, не изменило
`providerRevision().worktree`. Игнорируемые OpenSpec/HLV/Lekalo-файлы собираются
явно, а игнорируемые планы AI Factory — нет. Это пробел в привязке provider evidence;
проба не утверждает, что весь `/aif-done` обязательно пропустит такой случай.

Отдельно проверено: `.ai-factory/RULES.md` не входит в стандартный список источников
SessionBrief. После его изменения `inspectSessionBrief()` по-прежнему возвращает
`valid`. При этом [Base Context](context-loading-policy.md) включает этот файл.
Ссылка из `ARCHITECTURE.md` на другой документ также сама по себе не добавляет
целевой файл в список хешируемых источников: дополнительные источники должны
попасть в явный список. Сейчас для части таких документов есть `context_refs`.

Нужен общий список фактически используемых источников: план, задачи, требования,
верхнеуровневые и областные правила, применимые решения и инструкции, версии
форматов и адаптеров. Свежесть нельзя определять только по видимым Git-файлам.

### 5. `.ai-factory/specs` уже имеет другое значение

В classic-режиме [aif-done](../skills/aif-done/SKILL.md) копирует завершённый план
в `.ai-factory/specs/<plan-id>/`, создаёт итоговый `spec.md` и обновляет
`specs/index.yaml`. Этот `spec.md` описывает выполненную работу и проверки.

В OpenSpec `openspec/specs/<capability>/spec.md` описывает действующие требования
к возможности системы. Архив изменения и актуальная спецификация имеют разную
семантику. Нельзя просто перенести OpenSpec specs в старый каталог с таким же
именем без миграции, изменения читателей и сохранения прежних ссылок.

### 6. Обновление, архивирование и восстановление требуют разных правил

[ADR 0001](adr/0001-openspec-native-artifact-protocol.md) объединяет runtime и QA
в категорию удаляемых/восстанавливаемых данных. SessionBrief и generated rules
можно пересоздать из источников. Историческое наблюдение теста или ревью после
удаления восстановить таким способом нельзя: новый запуск создаёт новое evidence.

Сейчас provider evidence записывается в файл `<provider>-<phase>.json` и заменяет
предыдущее наблюдение этой фазы. Это текущее состояние, а не полный журнал запусков.
Кроме того, manual QA использует branch ID, а AIFHub verify/done — change ID.
Положительный результат одного вида QA не заменяет другой.

### 7. Git-политика runtime в проекте-потребителе

Исходная проблема ниже воспроизведена до исправления. Теперь bootstrap и writers
создают локальные `.gitignore`. Реальная установка текущих исходников через
AI Factory 2.18.1 в отдельный Git-проект подтвердила: default/custom runtime-файлы
после init игнорируются, сами `.gitignore` и планы/specs видны Git, повторный init
не меняет времена записи правил. Корневой `.gitignore` и индекс не менялись.

Проверено реальной установкой через локальный AI Factory **2.18.1**: отдельный
временный Git-проект, `init --agents codex --skills all --config`, затем
`extension add <snapshot>` с копией текущих исходников расширения. Команда
`aifhub-mode init` с включённым OpenSpec и отключёнными HLV/Lekalo создала skeleton.
Установленный helper записал указатель текущего изменения; установленная команда
`aifhub-write-gate-evidence` записала синтетический QA-отчёт для проверки хранения.
Внешние OpenSpec/HLV CLI и модельные проверки не запускались.

Установщик сохранил `.gitignore` расширения внутри
`.ai-factory/extensions/aifhub-extension/`, но корневой `.gitignore` потребителя
остался неизменным. Вложенные правила не распространяются на соседние каталоги
`.ai-factory/state/` и `.ai-factory/qa/`. Bootstrap расширения также не добавил
правил для них.

Проверка без пользовательских global excludes дала:

```text
git status --short --untracked-files=all -- .ai-factory/state .ai-factory/qa
?? .ai-factory/qa/git-audit/rules.md
?? .ai-factory/state/current.yaml

git add --dry-run -- .ai-factory/state .ai-factory/qa
add '.ai-factory/qa/git-audit/rules.md'
add '.ai-factory/state/current.yaml'
```

`git check-ignore` для этих файлов завершился с кодом 1. После добавления точечных
правил в корневой `.gitignore` тестового потребителя оба файла стали игнорироваться,
а контрольные файлы в `.ai-factory/plans/` и `.ai-factory/specs/` остались видны Git.
Индекс не изменялся. Пустые каталоги Git не хранит; проблема возникает после
записи файлов и последующего `git add`, а не из-за самого создания каталогов.

Следовательно, `.gitignore` репозитория расширения не является защитой потребителя.
Реализованное решение — создавать `.gitignore` внутри каждого runtime-каталога
при его создании, включая реальные настроенные пути и уже установленные проекты:

```gitignore
*
!.gitignore
```

Такой файл хранится в Git и передаёт правило другим checkout, а временное содержимое
каталога исключается. В отдельном Git-проекте проверены default state/QA/generated
и произвольный `custom/runtime/`: `git add --dry-run .` выбирает только сами
`.gitignore` и контрольные планы/specs; вложенные runtime-файлы не выбирает.
Корневой `.gitignore` для этой проверки не создавался. Если вышестоящие правила
уже исключают весь каталог, вложенное исключение `!.gitignore` их не отменяет.

Создание выполняет [общий helper](../scripts/runtime-gitignore.mjs) при подготовке
runtime-каталогов. Он подключён к bootstrap, указателям, SessionBrief, кэшу
контекста, QA/provider evidence, migration reports и generated rules. Bootstrap
обрабатывает настроенные state/QA/generated пути и фиксированные defaults,
которыми ещё пользуется часть writers. Это не исправляет остальные расхождения
resolver-путей из пунктов выше.

Существующие пользовательские `.gitignore` сохраняются побайтно, даже если их
правила разрешают отдельные файлы. Повторный запуск не меняет время записи файла.
Dry-run показывает недостающие правила без создания каталогов; status/doctor
и status/show SessionBrief остаются без записи. Ссылки, hard links, выход из
проекта и канонические roots отклоняются. Helper не меняет индекс Git.

После обновления установленного расширения нужно выполнить
`ai-factory aifhub-mode init --json`, чтобы создать правила в существующих
runtime-каталогах. Сам `extension add/update` по-прежнему не запускает bootstrap.

## Куда хранить: целевая карта для проекта-потребителя

Пути ниже — defaults или явно помеченные предложения. Настроенные пути должны
проходить через единый resolver. Таблица задаёт назначение материалов, а не
утверждает, что все читатели уже поддерживают эту раскладку.

| Материалы | Место | Кто обновляет и как долго храним |
|---|---|---|
| Конфигурация проекта | `.ai-factory/config.yaml` | Bootstrap и владелец соответствующей настройки; сохранять в Git безопасную проектную конфигурацию |
| Метаданные установки | `.ai-factory.json` | Установщик AI Factory; используется в том числе для определения версии, не расширять произвольными требованиями |
| Описание проекта и обзор архитектуры | настроенные `DESCRIPTION.md`, `ARCHITECTURE.md` | Владельцы analyze/architecture; сохранять текущий обзор и ссылки на подробные документы |
| Документация для людей | `README.md`, `paths.docs` → `docs/` | Документационный workflow; инструкции использования, эксплуатации, интеграции и API; Git |
| Принятые ADR и подробные C4 | предлагаемая конвенция `docs/adr/`, `docs/architecture/`, связанная с `ARCHITECTURE.md` | Оформление через архитектурный/документационный workflow; ADR сохранять с историей и статусом замены; C4 отражает текущую архитектуру |
| Действующие требования системы | целевой `paths.specs` → `.ai-factory/specs/<capability>/` **после миграции legacy-архива** | Владелец спецификаций; изменение через проверенный план; Git, независимый от plan ID идентификатор возможности |
| План и материалы конкретного изменения | `paths.plan` или `paths.plans`, формы описаны ниже | Планировщик владеет запросом, областью и заданиями; исполнитель обновляет единственное состояние задач; Git для сохраняемых планов |
| Предлагаемые изменения требований, истории и сценарии | секции плана или явно зарегистрированные документы его комплекта | Авторитетны для области данного изменения; сохранять идентичность требований и связи с принятыми specs |
| Исследования и черновики решений | `paths.research` → `.ai-factory/RESEARCH.md`; для ultra — `.ai-factory/research/<topic>/` при стандартном пути | Explore; гипотезы и альтернативы сохраняются как исследование. В план переносится выбранный вывод с привязкой к источнику |
| Проверенные справочные материалы | `paths.references` → `.ai-factory/references/<topic>/` | Reference workflow; источник, версия, дата проверки, область применимости; полезные очищенные заметки можно хранить в Git |
| Правила проекта | `paths.rules_file` → `.ai-factory/RULES.md`, `paths.rules` и configured area rules | Соответствующие владельцы правил; один источник каждого правила, ссылки вместо расходящихся копий; Git |
| Терминология и политика ревью | `paths.context` → `CONTEXT.md`; `reviews.policy_file` → `REVIEW.md` | Glossary/review-policy ownership; постоянные термины и правила внимания, без результатов отдельных ревью; Git |
| План развития | `paths.roadmap` → `.ai-factory/ROADMAP.md` | Roadmap; конечные результаты связывать с планами, verify и внешними work items без смешивания их состояний |
| SessionBrief, указатели и рабочие записи | целевой `<paths.state>/<plan-id>/context/`, соседние `implementation/`, `fixes/` | Compiler/execution; локальный runtime. Brief пересобирается, значимые выводы из записей переводятся в постоянные документы |
| Кэш прочитанного контекста | `<paths.state>/context-dedup/session-<hash>/ledger.json` | Dedup; принадлежит сессии, хранит метаданные чтений, не является памятью проекта или спецификацией |
| Результаты verify, review, security, provider checks | целевой `<paths.qa>/<plan-id>/`; manual QA отдельно адресуется branch ID | Владелец соответствующей проверки. Для истории нужен явный run ID и сохранение точной проверенной версии; Git для очищенных итогов либо хранилище CI/artifacts |
| Generated rules и представления инструментов | существующий `.ai-factory/rules/generated/`; расположение других представлений задаётся адаптером | Генератор; производные данные с source digest, доступные для пересоздания, без самостоятельного статуса выполнения |
| Архив планов и итогов изменений | `paths.archive` → `.ai-factory/archive/plans/` | Archive/finalizer после выполнения условий; сохранить запрос, задачи, решения, ссылки на доказательства и прежнюю идентичность; Git или долговременное хранилище |

`CONTEXT.md` здесь уже является словарём терминов. Произвольную память агента,
журналы, требования и полный контекст задачи туда складывать нельзя без изменения
его существующего контракта. `AGENTS.md`/`CLAUDE.md` дают инструкции и навигацию;
читатели продолжают обращаться к настроенным проектным документам.

## Как оформить материалы плана

Сохраняем upstream-формы:

```text
fast:  <paths.plan>                       # default .ai-factory/PLAN.md
full:  <paths.plans>/<plan-id>.md
ultra: <paths.plans>/<plan-id>/index.md    # upstream marker + phase files
```

Для обычной задачи достаточно секций исходного запроса, требований/историй,
сценариев, решений, задач и проверок в одном плане. Общие ADR, C4, правила,
спецификации и справочные материалы подключаются ссылками с идентификаторами.

Если методологии нужны отдельные файлы, будущий контракт должен описать их как
инвентарь документов плана. Каталог `<plan-id>/` уже участвует в classic companion
и ultra discovery. Перед добавлением новых файлов туда нужно согласовать reader,
тип комплекта, единственный список задач и атомарное архивирование. Само имя
`index.md` не является достаточным основанием объявить любой комплект ultra.

Минимальные данные общего интерфейса плана:

- plan ID, точный исходный work item и native entrypoint;
- версия формата, основной формат требований, дополнительные виды документов;
- public mode и SDD profile;
- task/requirement IDs и ссылки на критерии приёмки;
- список авторитетных документов с назначением и владельцем записи;
- отдельно вычисляемая ревизия используемых источников и версия адаптера.

Добавление таких полей и многодокументного комплекта является работой расширения;
upstream не начинает автоматически понимать произвольный `plan.json`.

## Инструменты и обмен

OpenSpec поддерживает native changes/specs/archive и документирует выбор Store.
Однако текущий AIFHub runner/resolver не подключает `--store` как production
механизм выбора плана. Нужна проверка на точной поддерживаемой версии, что операции
чтения, validate, apply и archive используют одну выбранную область хранения.

Пока такого адаптера нет, имеющиеся `openspec/changes` и `openspec/specs`
продолжают обслуживаться текущим OpenSpec-native контрактом. Их перенос сам по
себе не реализует новую архитектуру. Native представление инструмента должно
иметь привязку к источнику; правки инструмента возвращаются через workflow
владельца плана, с проверкой версии и разрешением конфликтов.

HLV продолжает читать собственный `project.yaml` либо `.hlv/project.yaml` и
настроенные им пути. Его контракты связываются с требованиями и задачами через IDs.
Наличие каталога `.hlv` не даёт основания переносить туда весь контекст проекта.
Поддержка реального Lekalo provider protocol в проверенном коде ещё не реализована;
для неё пока нельзя обещать конкретную работающую раскладку файлов.

## Git, история и восстановление

- Сохраняемые планы, принятые спецификации, ADR, документация, правила и проектная
  конфигурация должны иметь долговременную историю. Если выбран Git, проверять
  `git check-ignore` для реальных путей; имя `.ai-factory` само по себе ничего не
  гарантирует. Политику `.gitignore` самого расширения не копировать в потребителя.
- Для default-путей runtime создаются локальные `.gitignore` в
  `.ai-factory/state/`, `.ai-factory/qa/` и `.ai-factory/rules/generated/`.
  Корневые правила для этих каталогов также работают, но локальные файлы позволяют
  хранить политику рядом с артефактами и поддерживать custom paths без их перечисления
  в корневом `.gitignore`.
  Перед исключением всего QA-каталога отделить переиспользуемые тестовые сценарии
  и сохраняемые итоги: например, перенести их в `docs/qa/`, материалы плана или
  artifact storage согласно назначению. Для custom paths использовать реальные
  разрешённые пути. Правила должны сохранять существующий `.gitignore` и не
  скрывать всю `.ai-factory/`. Уже отслеживаемые файлы новое правило не исключает
  из индекса; их обработка требует отдельной миграции.
- Для fast-плана upstream допускает удаление после исполнения. Если запрос и
  решения нужны для аудита, сначала обеспечить их сохранение/архивирование.
- Brief, индексы, generated views и кэши можно пересоздать только из доступных
  источников с известными версиями. Рабочие заметки, исход которых больше нигде
  не зафиксирован, не считать автоматически восстанавливаемыми.
- Проверка после удаления QA — новый запуск. Для подтверждения прежнего результата
  сохранять старое наблюдение в Git или artifact storage согласно политике проекта;
  отсутствие файла не превращается в прежний PASS.
- Provider JSON хранит ограниченное структурированное evidence. OpenSpec verifier
  сейчас также сохраняет stdout/stderr под `qa/<id>/raw/`; эти файлы нельзя
  автоматически публиковать как обычную документацию. Общие материалы для команды
  должны содержать только необходимые безопасные данные и ссылки на доказательства.
- Архив не становится источником текущего поведения только потому, что назван
  `spec.md`. Действующие требования, исторический результат и новая проверка имеют
  отдельные идентичности и правила изменения.

## Порядок последующей реализации

1. Согласовать общий resolver путей и список владельцев/источников. Разделить
   постоянные specs и legacy-архив с сохранением ссылок и статусов.
2. Исправить совместимость SessionBrief с `aifhub.tools`, использование `paths.state`
   и полноту зависимостей контекста; проверить edit/delete/add для каждого источника.
3. Привязать provider evidence к тому же списку источников, включая игнорируемые
   планы, и исключать реальные настроенные runtime/QA/generated paths.
4. Определить форматы документов плана и поведение архивирования для native
   fast/full/ultra. Подключить адаптеры и проверить реальные tool round trips.
5. Создание локальных `.gitignore` реализовано в общем helper подготовки runtime.
   При миграции существующих проектов отдельно разобрать уже отслеживаемые файлы
   и постоянные QA-сценарии; автоматическое исключение из индекса не выполняется.
6. Ввести политику истории запусков и хранения evidence. Лишь после этих шагов
   менять действующие инструкции владельцев и выполнять миграцию проектов.
