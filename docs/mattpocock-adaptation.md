# Адаптация mattpocock в скиллах AIFHub

[Issue #164](https://github.com/ichinya/aifhub-extension/issues/164) посвящён скиллам mattpocock. Цель этой адаптации — усилить существующие скиллы AIFHub полезными практиками из этого источника. Первый этап добавляет делегирование исследований и сравнение интерфейсов в текущие explore/plan/improve команды. Дополнительные адаптации улучшают подготовку задач, диагностику, тестирование, архитектурный поиск и review. Полный внешний набор скиллов и отдельный lifecycle не устанавливаются.

Исходный аудит выполнен 2026-09-06: AIFHub `bc93bda969e6dd30d54db5b9cc36953f5ca15982`, базовый AI Factory `3c1ddd4740d7b1c30d8ecb3dc80fa5e7b8d7ef5a`, mattpocock `3cca18b368ae95cdbdebbff572ccafa662551015`. Это сравнение инструкций и источников, не измерение качества или стоимости моделей.

## Первый этап

Общие инструкции находятся в [RESEARCH-DESIGN.md](../skills/shared/RESEARCH-DESIGN.md). Их условно загружают:

- [aif-explore](../injections/core/aif-explore-plan-folder.md) — для независимого поиска фактов; до подтверждения brief сохраняются границы короткого интервью;
- [aif-plan](../injections/core/aif-plan-plan-folder.md) — для независимых исследований и существенного выбора интерфейса после проверки режима и версии;
- [aif-improve](../injections/core/aif-improve-plan-folder.md) — для затронутой части существующего дизайна после классификации плана;
- plan-polisher agents для [Codex](../agent-files/codex/aifhub-plan-polisher.toml) и [Claude](../agent-files/claude/aifhub-plan-polisher.md) — для работы по заданным источникам без вложенного делегирования.

Обычный короткий поиск, механическое уточнение плана или уже выбранный интерфейс остаются прямой задачей агента в пределах текущей команды. При отсутствии subagent capability применяется тот же анализ локально.

Координатор разделяет вопросы по способу разрешения: факт из источника, техническая альтернатива, решение пользователя или необходимый эксперимент/доступ. Независимые фактические вопросы можно исследовать одновременно. Ожидание одного факта блокирует только зависимые вопросы. Субагенты не отвечают за пользователя.

В назначении есть цель, ограничения, ожидаемый результат, доступные источники и их ревизия, инструменты и область чтения. Для незакоммиченного кода передаются снимки или hashes: один HEAD не описывает рабочее дерево. Ссылки используются только когда получатель действительно может прочитать соответствующий источник. Иначе передаётся разрешённый фрагмент с его идентичностью или указывается отсутствие данных.

Каждый исследователь возвращает ответ на все назначенные вопросы, прямые доказательства, отдельно выводы и неизвестности. Координатор сверяет существенные факты с источниками, проверяет изменившиеся входы и разбирает противоречия. Частичный ответ не закрывает всё назначение.

Для существенного выбора интерфейса сравниваются два-три разных подхода, включая существующий как baseline. У них общие требования и acceptance examples, но разные цели проектирования. Результат включает пример одного и того же вызова, инварианты, ошибки, размещение зависимостей, тестирование и стоимость миграции. Координатор рекомендует вариант по этим критериям; обычные технические детали остаются в пределах уже полученного разрешения. Неизвестные требования или архитектурные предпосылки остаются поводом для исследования: сравнение не обходит существующую маршрутизацию в `research`.

## Границы

- Решения и разрешения пользователя сохраняются. Каждый worker не начинает собственное интервью или подтверждение.
- До explore brief confirmation допустим только ограниченный поиск фактов. Полное исследование сохраняет существующий confirmation/re-entry contract.
- Исследовательские задания возвращают текст родителю; они не пишут документы, временные заметки за пределами проекта, runtime state или канонические артефакты. Запись выполняет уже разрешённый writer текущей команды; назначенный plan-polisher сохраняет свой scope уточнения плана после сверки доказательств.
- Committed Research Context и его rebase contract сохраняются. Glossary остаётся в ведении `/aif-analyze`.
- Классификация legacy ultra предшествует уточнению; валидный bundle возвращается upstream, malformed/collision прекращают обработку.
- Role-specific задания не создают новый SessionBrief, execution role, scheduler, QA gate или receipt. Существующий SessionBrief пока является [OpenSpec-only прототипом](sdd-profiles.md).

Расхождения с upstream намеренные: не переносится запрет конкретных путей в планах, обязательное согласование каждой поверхности тестирования, обязательное доказательство глобально минимального repro или автоматическая запись glossary/ADR. Сохраняются AIFHub ultra, artifact ownership, no-test и research contracts. Два прохода review остаются упорядоченными, с одним итоговым verdict; параллельны только независимые вопросы внутри текущего прохода.

При отсутствии subagent capability review выполняется локально с честным указанием независимости. Без доказательств по части scope полный PASS недопустим. Поддерживающий отчёт без shell не доказывает исполнение Git или тестов; он не заменяет установленный формат полного review-sidecar и не создаёт fresh-context receipt.

## Изолированное исполнение в основном workflow

Источник — [implement-spec](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/in-progress/implement-spec/SKILL.md), который upstream относит к `in-progress`: граф задач, отдельные worktrees исполнителей и последовательная интеграция результатов.

Существующие [отдельные результаты и небольшие batches](workflow-mechanics.md) сохраняются; batch остаётся одним назначением одному worker. Для параллельной реализации добавлен [изолированный путь](isolated-execution.md) через тот же execution helper и основной `/aif-implement`. Общий checkout по-прежнему привязан целиком к снимку; параллельные исполнители используют отдельные worktrees.

Реализованы следующие части:

1. Координатор регистрирует 1–5 независимых single-task runs до правок. Worktrees должны принадлежать одному Git repo и совпадать по HEAD, index, исходным файлам и каноническому контексту. Непересекающиеся точные scopes и завершённые внешние prerequisites проверяются при admission; смысловую независимость проверяет координатор.
2. Каждый локально принятый результат переносится отдельно. Координатор проверяет объединённое дерево перед интеграционной приёмкой и перед закрытием группы; текущая группа блокирует обычные назначения в интеграционном checkout.
3. Канонический checklist обновляется только после закрытия группы и свежего `isolation-resume`, строго по accepted set. Незавершённые задачи сохраняются; следующая группа строится из обновлённых задач и кода.
4. Durable journal хранит intent и образы файлов до переноса. Точный replay восстанавливает прерванный перенос/откат; неизвестный третий образ останавливает запись. Historical replay не даёт нового разрешения на прогресс. Abandonment сохраняет частичный код и историю без completion authority.
5. Существующие worker recovery contracts используются до retirement; создание/остановка процессов, подготовка и удаление worktrees остаются у host/владельца после сохранения нужных данных. Runtime не выполняет Git merge/commit или публикацию.

Это ограниченные группы готовых задач, а не произвольный DAG scheduler. Host должен уметь предоставить точные исходные snapshots, включая dirty work и разрешённый контекст; при отсутствии такой возможности исполнение остаётся последовательным. Лимиты: 100 файлов и 8 MiB сохранённых base64 образов на группу, 100 исторических групп на checkout. Helper проверяет переданные evidence и exit codes, но не запускает тесты и не подтверждает смерть процесса сам. Сохраняются [ADR 0005](adr/0005-ai-factory-plan-methodologies.md), ultra handoff и единый verify/done lifecycle. Исполняемые тесты используют настоящие временные Git worktrees и Node-проверки; полный установленный multi-agent host workflow и прирост качества моделей этим не измерены.

## Проверка первого этапа

Repository validators проверяют ссылки, extension boundaries, форматы и регистрацию agent files; существующие тесты проверяют прежние mode, interview, immutable-source и ultra contracts. Это проверка подключения инструкций, не исполнение arbitrary-agent workflow.

Независимый агент оценил следующий ответ и назначение по шести заданным ситуациям. Это моделирование решений по инструкциям: сценарные репозитории и полноценные workflow запуски не исполнялись.

| Ситуация | Наблюдаемое решение |
|---|---|
| Explore до confirmation; два независимых факта и нерешённый продуктовый вопрос | Ограниченные read-only задания по фактам; продуктовый выбор остаётся у пользователя |
| Существенное изменение lookup-интерфейса | Baseline и два разных design objectives при одинаковых ошибках и acceptance examples; неподтверждённые предпосылки возвращают в research |
| Одна сломанная ссылка при явном `plan full` | Прямое компактное планирование без workers; выбранная команда и границы записи сохраняются |
| Polisher получил сведения по R1, код уже R2 | Перепроверка затронутых фактов; авторизованное уточнение назначенного плана без вложенных workers и автоматического research rebase |
| Валидный legacy ultra | Существующий точный upstream handoff до локального сравнения или записи |
| Исследователь видит только разрешённый фрагмент | Выводы ограничены фрагментом; поведение полного источника остаётся неподтверждённым |

Проверка выявила неоднозначность write scope plan-polisher и недостаточно явные границы research profile и механических planning requests. Формулировки уточнены; повторная оценка затронутых сценариев 2–4 не выявила оставшихся существенных противоречий. Для заявления об улучшении качества или стоимости нужен отдельный сопоставимый baseline/variant запуск.

## Проверка дополнительных адаптаций

Независимый агент прочитал новые shared policies, соответствующие injections и парные agents, затем смоделировал следующий ответ и разрешённые действия по восьми ситуациям:

| Входная ситуация | Полученное решение |
|---|---|
| CSV parser уже есть, но сохранение и обработка повторного ID не определены | Частичное покрытие не объявлено готовой функцией; нерешённый продуктовый выбор направлен в research без добавления UI/БД-сервиса |
| Переименование общего экспорта при независимых релизах и старых внешних consumers | Expand–migrate–contract зависит от доступных совместимых версий; удаление старого имени остаётся условным |
| Запрошено только missing inline verification для выполненного и невыполненного пунктов | Сохранены оба ID, порядок, действия и checked state; вертикальные срезы не навязаны существующему checklist |
| Гонка: original 17/100 до и 1/100 после, single-caller 0/100, три failed experiments | Finding остался открытым; уменьшенный случай признан недостаточным; дальнейшие правки остановлены без сброса истории |
| Новый bug report без активного OpenSpec change и QA | Сохранён существующий planning handoff до fix writes |
| Незакоммиченный review: reports по разным ревизиям, missing added file, sidecar без shell | WARN с coverage gap, запрос точного контекста, без утверждения о запущенных тестах; один существующий gate block |
| Названа область orders, история содержит generated formatting, есть действующий ADR | Кандидат основан на текущих callers в orders; различия условий не объявлены дефектом без требований, ADR сохранён |
| Partial и whole-order cancellation расходятся по смыслу, rationale ADR неизвестен | Семантический вопрос не превращён в lexical правку glossary или готовое ADR; сохранены владельцы research и терминов |

Подтверждённых конфликтов новых правил с владельцами, classification или форматом sidecar в этих сценариях не найдено. Это оценка синтетических ситуаций, не исполнение полного установленного agent workflow и не замер прироста качества. Repository validators и 149 целевых тестов проверяют текущие prompt/artifact contracts, парные agent formats, review/glossary boundaries, bug-fix smoke и существующие executable test-quality examples. Отдельно проверены совпадение трёх добавленных парных agent sections и разрешение installed-reference ссылок в десяти consumers.
