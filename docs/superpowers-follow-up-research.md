## Исходные кандидаты — реализованы в PR #185

### 1. Проверять, какую ошибку способен обнаружить тест

Источник: [writing-good-tests.md](https://github.com/obra/superpowers/blob/b36e0829c6d0140e93cfef2ca599b1b07d4a7797/skills/test-driven-development/writing-good-tests.md).

В [implement injection](../injections/core/aif-implement-plan-folder.md) и [implement worker](../agent-files/codex/aifhub-implement-worker.toml) уже есть RED/GREEN/REFACTOR, но нет отдельного требования назвать реалистичную ошибку, которую ловит тест, и независимо получить ожидаемое значение. Это расширение качества проверок, а не повторное внедрение TDD.

Минимальный вариант для **#141**: добавить эти два критерия в существующую дисциплину тестирования. Для проверки взять пример, где обе стороны assertion вычисляются одним production helper: такой тест должен быть признан недостаточным. В исправленном тесте ожидаемое значение задаётся независимо, а заранее выбранная ошибочная реализация приводит к падению. Проверка наличия слов в prompt этого не доказывает. Не превращать предложение в обязательный mutation runner для каждого изменения; существующие docs-only и no-test исключения сохраняются.

### 2. Проверять конфликты задач до первого запуска исполнителя

Источник: [SDD pre-flight scan, строки 162–181](https://github.com/obra/superpowers/blob/b36e0829c6d0140e93cfef2ca599b1b07d4a7797/skills/subagent-driven-development/SKILL.md#L162-L181).

Локальный [implement worker](../agent-files/codex/aifhub-implement-worker.toml) ограничивает выполнение одной задачей или тесно связанной группой. Сопоставление задач, которые затрагивают общий файл или интерфейс, отдельным результатом сейчас не требуется.

Кандидат для **#141**, с согласованием ownership с **#168**: перед делегированием фиксировать пары пересекающихся задач, что одна производит и другая использует, обнаруженное противоречие и выбранный порядок. Это supporting runtime evidence существующего координатора; новый формат и путь пока не определены. Проверка: две задачи задают несовместимые сигнатуры одного интерфейса — противоречие должно стать видимым до edits. Совпадение файла без конфликта не должно само по себе блокировать работу. Материальное изменение требований остаётся у владельца canonical artifacts.

### 3. Повторно проверять исправление по прежним findings и точному diff

Источник: [scoped re-review prompt](https://github.com/obra/superpowers/blob/b36e0829c6d0140e93cfef2ca599b1b07d4a7797/skills/subagent-driven-development/re-review-prompt.md).

В [review injection](../injections/core/aif-review-context-providers.md) и [review sidecar](../agent-files/codex/aifhub-review-sidecar.toml) уже закреплены два прохода и общий verdict. Отдельного входа с прежними finding IDs, точными base/head исправления и результатом по каждому finding нет.

Кандидат для **#141**: ограниченный повторный review исправления с доказательством для каждого закрытого finding и поиском новых дефектов в fix diff. **#168** продолжает владеть fresh-context profile и receipt. Проверка: одно исправление устраняет исходный дефект, другое сохраняет его, третье создаёт регрессию — все три ситуации должны различаться в выводе. Ограничение числа раундов не может превращать незакрытый blocking finding в PASS. Этот режим не заменяет явно требуемый независимый review или `/aif-verify`.

### 4. Явно группировать небольшие однотипные задачи

Источник: [SDD, Batch small same-shape work](https://github.com/obra/superpowers/blob/b36e0829c6d0140e93cfef2ca599b1b07d4a7797/skills/subagent-driven-development/SKILL.md#L223-L229).

Разрешённая сейчас тесно связанная группа в [implement worker](../agent-files/codex/aifhub-implement-worker.toml) не равнозначна набору независимых однотипных правок. Расширение этой границы требует явного решения, а не интерпретации существующего разрешения.

Кандидат для **#141**: разрешать ограниченный batch только с полным перечнем задач, файлов и ожидаемых изменений; принимать результат отдельно по каждому элементу. Проверка: исполнитель изменяет четыре из пяти перечисленных файлов — пятая задача остаётся незавершённой. Задачи с зависимостями или разным риском нельзя объединять только ради уменьшения числа запусков. Автоматическую экономию стоимости не обещать без измерений.

### 5. При ожидании готовности проверять условие, а не фиксированную задержку

Источник: [condition-based-waiting.md](https://github.com/obra/superpowers/blob/b36e0829c6d0140e93cfef2ca599b1b07d4a7797/skills/systematic-debugging/condition-based-waiting.md).

[Fix injection](../injections/core/aif-fix-plan-folder.md) уже требует root-cause evidence и одинаковую проверку до/после исправления. Отдельного правила для устранения flaky ожиданий там нет.

Кандидат для **#141**: при ожидании асинхронной готовности проверять наблюдаемое условие с ограниченным timeout. Проверка: готовность наступает с разной задержкой либо не наступает вообще; тест должен соответственно завершаться успешно или ограниченно падать. Для debounce, throttle и других проверок самого времени задержки остаются частью предмета тестирования. Не запрещать timing-тесты и не увеличивать sleep как универсальное исправление.

## Что уже покрыто или остаётся у другого владельца

- **Уже адаптировано:** RED/GREEN/REFACTOR, поиск root cause с одной гипотезой и экспериментом, plan/spec review перед quality review, supporting evidence и authoritative `/aif-verify`. Повторное объявление этих идей новыми не обосновано.
- **Частично покрыто:** [QUESTION-TOOL.md](../skills/shared/QUESTION-TOOL.md) уже требует от автономных агентов возвращать assumptions и blockers родителю. Возможная долговечная запись решений — отдельное расширение, а не отсутствие правил автономной работы.
- **#168:** SDD profiles, SessionBrief, plan compliance/drift, fresh-context review, tracer и измеряемая context policy. Здесь не предлагаются альтернативные schemas или пути для них.
- **Модели:** в [Codex implement worker](../agent-files/codex/aifhub-implement-worker.toml) уже явно задан `gpt-5.4`, в [Codex review sidecar](../agent-files/codex/aifhub-review-sidecar.toml) — `gpt-5.4-mini`; `inherit` используется в [Claude implement worker](../agent-files/claude/aifhub-implement-worker.md). Вывод об отсутствии выбора моделей во всех runtime неверен. Динамический routing требует отдельной проверки возможностей и стоимости.
- **Не переносить автоматически:** обязательное повторное approval для любой задачи, новый plugin/bootstrap/worktree слой, закрытие blocking findings по достижении лимита раундов, обязательную валидацию на всех слоях после любого fix. Эти правила могут расширить scope или ослабить действующие границы.

Исследовательские запуски использовали OMP **18.1.10**. Отчёты моделей были входом для проверки по источникам; их предложения не считаются автоматически принятыми.

| Запуск | Наблюдавшийся результат | Как использован |

| `omni/glm/glm-5.3-flash` | Исследование завершено | Идеи сопоставлены с upstream и локальными файлами |
| `omni/koda/koda-base` | Исследование завершено | Исправлены выводы о моделях Codex; исключены повторные approval и недостаточные проверки только по тексту prompt |
| `omni/bai/deepseek-v4-flash` | Ошибка доступа/кредитов, отчёта нет | Исследовательских выводов не добавляет |

Для CFP проведена дополнительная проверка 2026-09-05 через `openai-responses` в отдельных OMP-сессиях с точным model ID, `max` и без fallback:

| Проверка | CFP DeepSeek | Контроль GLM на той же установке |
| --- | --- | --- |
| Точный короткий текстовый ответ | PASS | Не запускался |
| Прочитать неизвестную модели строку через `read` | FAIL: 0 вызовов, 0 результатов инструментов | PASS: настоящий `read`, строка совпала |
| Вычислить SHA-256 файла через `bash` | FAIL: 0 вызовов, 0 результатов инструментов | PASS: настоящий `bash`, digest совпал |

Методика: создать временный файл со случайной строкой; независимо вычислить его SHA-256; передать модели только путь и требуемое действие. Для инструментального PASS нужны правильный ответ, структурный `toolCall` нужного инструмента и связанный успешный `toolResult` с ожидаемым значением. Выход OMP с кодом 0, обещание выполнить действие или текстовый маркер вызова не удовлетворяют проверке.

Все три CFP-процесса завершились с кодом 0 без transport errors, но только текстовый тест дал требуемый результат. В более ранних полных запросах также наблюдались обрывы потока; они не доказывают общую недоступность модели. Отдельный прежний запуск через Chat Completions тоже вернул вызов чтения текстом. Причина и её расположение в модели, gateway или клиенте не установлены; эти результаты ограничены проверенными маршрутами, версиями и датой. Контроль GLM подтверждает работоспособность процедуры, но не является сравнительным benchmark качества моделей.

В репозиторий включена только эта сводка: без сырых сессий, скрытых рассуждений, абсолютных путей рабочей машины, случайной строки, credentials или backend-конфигурации. Результаты не меняют модельные настройки продукта.

## Результат реализации и границы проверки

Все пять пунктов реализованы в инструкциях для **#141**. Координатор проверяет межзадачные и внутренние противоречия, явно задаёт состав небольшого batch и сверяет результат по каждому элементу. Fixer передаёт исходные finding IDs и точные версии до/после исправления; re-review проверяет каждый finding и весь fix diff, сохраняя blockers при неполных данных. **#168** продолжает владеть profiles, SessionBrief, fresh-context receipts и tracer. Prompt contract проверяет подключение и парность инструкций; executable examples проверяют поведение примеров тестов и ожиданий. Это не доказывает соблюдение правил произвольной моделью. Merge, закрытие issue и отдельная оценка поведения моделей не выполняются автоматически.
